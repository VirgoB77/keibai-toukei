# 競売統計（収集用・非公開）

> **このリポジトリを public にしない。**
> `inbox/` と `data/raw/` に、入札中の物件の所在地が生のまま入る。
> 人が住んでいる可能性があるもので、3.1 で個票にしないと決めたもの。
> git の履歴は消せないので、public にした日に過去のぶんまで全部公開される。
> ファイルを消すコミットを積んでも、履歴から取り出せる。
> 公開するのは、ここで作った集計と生成HTMLだけ。**別のリポジトリに送る。**


**差し押さえられた土地が売られる**のは、競売（裁判所）と公売（税）の2通りある。
どちらも結果がすぐ消えるので、毎日ためれば、いつか誰も持っていない記録になる。
大阪府・兵庫県の分を追う。

物件一覧を読むところまで動いている（2026-09-17 時点で 4庁 / 46市区町村 / 106件）。
**出すのは集計だけ。** 1件1行のデータは公開側に出さない。
入札中の情報で、人が住んでいる建物を含むため。

姉妹サイト4つで守る決まりの**正本**は、大型店日報のリポジトリにある。

## 棚は2段

| 段 (`system`) | 何か | 売り手 | 根拠になる制度 |
| --- | --- | --- | --- |
| `keibai` 競売 | 借金の担保などを裁判所が強制的に売る | 裁判所（大阪3庁・神戸3庁） | 民事執行法 |
| `kobai` 公売 | 税金の滞納で差し押さえた財産を売る | 税務署・自治体の税務課 | 国税徴収法・地方税法 |

**国有財産・公有財産の売払いは、ここでは扱わない（2026-09-15 決定）。**
学校跡地・庁舎跡地・市有地・国有地の売却は、国や自治体が**自分の財産**を
一般競争入札で売るもので、滞納処分による公売とは**別の制度**。混ざらないよう
姉妹サイト側に置く。調べた収集先は消さずに `handoff: "姉妹サイト"` と印を付けて
`sources.json` に残してある（同じところを何度も調べ直さないため）。

設計書 [DESIGN.md](DESIGN.md) は4段で書かれているが、そこは**この README が新しい**。

**競売と公売は個票を出さない（確定）。** 理由は2つ。

1. **規約の確認が終わっていない。** BIT は「本来の趣旨以外の目的での使用」と
   「無断転載」を禁じている。集計がこれに当たるかは弁護士に見てもらう項目として
   残っている。件数と中央値だけなら「数値や事実に著作権はない」で説明がつくが、
   1件ずつ並べると正面からぶつかる
2. **その家には、まだ人が住んでいることがある。** 入札中の物件は、
   住んでいる人がいる状態で出ている。落札後も「あの住所は競売だった」と
   検索に出続けるのは重すぎる。しかも所有者名は裁判所も税務署も公表していないので、
   「法人だから出してよい」と**確かめる方法がない**

理由に「個票では儲からないから」は入れない。儲かる方法が見つかったときに
判断がひっくり返ってしまう。**2は、儲かっても変わらない理由**なので、これで足りる。

## 取るのは全部、絞るのは出すときだけ

**集めるときに下限を置かない。生データは全部 `data/raw/` に残す。**
絞り込みは出力（公開）の段階だけでやる。基準を後から変えたときに、
取り直しが起きないようにするため。

これは設計書 1.4 の「競売・公売は住所を行データにも市区町村までしか持たない」を
**置き換える**（2026-09-15）。行データには元のまま持ち、
**公開するときに落とす**。公開される住所は次の2通りだけ。

| 出すもの | 住所の細かさ |
| --- | --- |
| 一覧（`data/public/index.json`） | 市区町村まで（政令市は区まで） |
| 跡地（`atochi.json`） | 町丁目まで。**人が住んでいないと分かっていて、落札が済んだものだけ** |

地番・住居表示・建物名・部屋番号は、**どの公開ファイルにも出さない。**

## いちばん大事な決まり

**BIT（不動産競売物件情報サイト）から3点セットを絶対に取らない。**

3点セット（物件明細書・現況調査報告書・評価書）は個人名こそ伏せてあるが、
地番も室内写真も生活の様子も残っている。統計には要らないものなので、近づかない。

守り方は2重にしてある。

- `recon.py` は **BITのページからリンクを1本も辿らない**。何が置いてあるかを数えて報告するだけ
- BITから `application/pdf` が返ってきたら、中身を捨ててレポートに出す

この2つは `tests/test_recon.py` で固定してある。壊すとテストが落ち、
GitHub Actions は**取りに行く前に止まる**。

## 使い方

### GitHub の画面から動かす（手がかからない・パソコン不要）

1. リポジトリの **Actions** タブを開く
2. 左の「**役所の土地ウォッチ（偵察・保存）**」を選ぶ
3. 右上の **Run workflow** を押す

   または収集先の id を入れる。空なら全部）
4. 終わったら、実行結果の画面にそのままレポートが出る

**自分のパソコンでは何も動かさなくてよい。** 動かしているのは GitHub のサーバー。

走るたびにページの中身をそのまま `data/raw/` に保存するので、
**git の履歴がそのまま「いつ何が変わったか」の記録になる**。
差分を調べるしくみを自分で書かなくてよい。

自動を止めたいときは `.github/workflows/keibai.yml` の `schedule:` の3行を消す。

## 数字の出し方（`aggregate.py`）

個票を出さないぶん、数字を厚くする。升は **市区町村 × 種別 × 段階 × 月**。

### 段階を混ぜない

**まだ開札していない回と、結果が出た回を同じ升に入れない。**
意味がまったく違うため（`公告` と `結果` に分けてある）。

段階の言い方は姉妹サイト共通で **予定／公告／結果** の3つ。
その中の内訳は「`-`」でつなぐ。

| 段階 | 何を数えるか | どの月に入れるか |
| --- | --- | --- |
| `公告` | その月に公告された**回**の数（新規＋再公告）。市場の厚み | 初めて見た日の月 |
| `公告-初出` | そのうち、**こちらが初めて見た**回だけ。「初めて公告された」ではない | 同上 |
| `公告-再出` | そのうち、**こちらが前にも見ている**回。**いまは記録が1日分しかないので構造的に0** | 同上 |
| `結果` | その月に開札された回の数（落札＋不調）。**落札率の分母** | 開札のあった月 |
| `落札` | そのうち売れた回。**落札率の分子** | 同上 |
| `不調` | そのうち売れなかった回 | 同上 |

**出しているのは内訳（子）だけ。** `公告` と `結果` は合計（親）なので、
`data/agg/monthly.json` にも `data/public/index.json` にも出さない。
読者は子を足せばよい（正本 3.2）。

### 結果の語は 落札／不調 の2つだけ（正本 6節・2026-09-19）

「売却」「不売」「売却済み」とは書かない。法令に近く、いちばん多く
使われていた語に4サイトでそろえた。**相手のページに書いてある語は別**で、
そちらは読むためのものなので、そのまま残す（`aggregate.py` の `SOLD`／`UNSOLD`）。

    種別には段階も結果も入る
    段階なら 競売/公告、結果なら 競売/落札・競売/不調
    **段階と結果を1つの升に混ぜない**
    種別の中をさらに分けるときは - でつなぐ（競売/公告-初出）

前は `結果-落札` と書いていた。**これが「混ぜた」形。**
段階（結果）と結果（落札）が1つの升に入っていた。

`取下げ` と `不明` は段階にしない。`取下げ` は位置ではなく値、
`不明` は値ではなく徴候（正本 9節）。升は作らず、数だけ `index.json` の
`not_counted` に出す。

### 足したときに数が合うこと（正本 3.2・2026-09-19）

    升の合計 ＋ not_counted の3つ ＝ 見た行の数
    合わなければ、黙って落としている

**この形のままでは、このサイトでは閉じない。** 1つの行が2つ以上の升に入り、
取下げになった行は公告の升にも入ったまま残るため（母集団の保存が先）。
実測で `106 ＋ 1 ＝ 107 ≠ 106` になった。だから2つに分けて確かめている。

| 何を | どう確かめるか |
| --- | --- |
| 行方の保存（在庫） | 1行は必ず1つの行方に入る。落札／不調／取下げ／消えた／読めない／待ち を足すと見た行の数 |
| 内訳の保存（流量） | 子の升を足すと親の升になる（公告＝公告-初出＋公告-再出、結果＝落札＋不調） |

合わない日は `index.json` を作らずに止まる。中身は
`data/parse-unknown.md` の「数が合うこと」に出る。
食い違いは正本に報告ずみ（`docs/seihon-toiawase.md` #11）。

**「結果」と「落札」を分けるのが大事。**
「売れた件数」をレコード数で数えると、不調まで混ざって水増しになる。
姉妹サイトの実測では、兵庫県の県有地売払いで **82回中61回（74%）が不調**だった。
分けていないと、売れた数が4倍近く多く見える。

**「いま入札中の件数」（ストック）では数えない。** それだと、
9月に出て10月も残っている物件を、10月にもう一度数えてしまう。

**数えるのは物件ではなく「回」。** 競売には

```
9月 公告 → 10月 開札 → 不調 → 11月 また公告
```

という流れがある。物件で数えると、11月の公告が消えてしまう。

**新規と合計を必ず分ける。** 混ぜると、不調が続く不況期に件数が勝手に増えて、
「市場が活発になった」と**逆に読める**。これがいちばんこわい間違い。
新規だけを見れば「新しく出た担保」、合計を見れば「今月の市場の厚み」が分かる。

1つの回が2つ以上の升に入る。9月に公告されて10月に売れた回は、
9月の `公告` と10月の `落札` の両方に1ずつ入る。
どちらも「その月に起きたこと」なので、二重計上ではない。

### 鍵に入れていいもの・だめなもの

**あとから訂正される値を鍵にしない。** 訂正公告で書き換わると、
同じ回が2つに増えてしまう。

| 入れていい | 入れない |
| --- | --- |
| 事件番号・物件番号・回（開札日）・段階・公告日 | 落札金額・応札者数・結果・面積・用途 |

行の鍵は `<裁判所>:<事件番号>:<物件番号>:<開札日>`。
物件そのものの鍵（`property_key`）は回を外したもので、再公告の判定に使う。

そのために、一覧を取るたびに**その日の分をそのまま残す**（スナップショット）。
`inbox/` に置いたページは消さず、取り込んだあとも置いたままにする。
一覧は上書きされるので、残していないと「いつ初めて出たか」が作れない。
`parse.py` が日付の古い順に重ねて、各物件の `first_seen` / `last_seen` を作る。
その日の一覧から消えた物件には `gone_on` を書いて、裏取り待ちにする。


| 出すもの | 中身 |
| --- | --- |
| `count` | 件数（機械用）。1〜2件は `null` |
| `count_label` | 件数（人に見せる用）。1〜2件は `"1-2"` |
| `base_median` | 売却基準価額の中央値 |
| `sale_median` | 売却価額の中央値 |
| `ratio_median` | 落札率（売却価額 ÷ 売却基準価額）の中央値 |
| （`unsold` 欄は無い） | **不調は升の段階として出す**（`競売/不調`）。取消は回の語なので升にしない |

**中央値にするのは、1件の高額物件で平均が壊れるから。**
郊外の戸建てが並ぶ中に1件だけ商業ビルが混じると、平均は跳ね上がって役に立たなくなる。

**不調は、ほかがどこも出していない。** BIT も民間サイトも「売れたもの」しか残さない。
「出したけれど売れなかった」が月ごとに分かるのは、ここだけになる。

### 3つのガード（崩さない）

1. **市区町村より下の粒度に下りない。** 町丁目・学区・地番では束ねない
2. **期間は月単位以上。** 週ごと・日ごとにしない
3. **1つの升が1〜2件のときは実数を出さない。**
   `count` を `null` にして、`count_label` に `"1-2"` と書く。
   **両方いる。** `count_label` だけだと足し算ができず、
   `count` だけだと、伏せたのか本当に0件なのかが見分けられない

段階で分けたぶん升は細かくなる。そのぶん1〜2件の升が増えるので、
このガードはいちばんよく効く場所になる。

理由は同じひとつ。**小さい自治体では、件数が1件と分かるだけで物件の特定につながる。**
「猪名川町の9月の戸建て競売＝1件」と書けば、その町の人には誰の家か分かってしまう。
1と2は、そこへ近づく道を最初から塞ぐため。3は、塞ぎきれなかったぶんの最後の蓋。

中央値も、元になる件数が3未満なら `null` にする（DESIGN 7章の秘匿ルール）。
このガードは `tests/test_aggregate.py` で固定してある。

## 姉妹サイトと突き合わせる（共通インデックス）

鯨屋（くじらや）の3サイトを、**住所**でつなぐ。

| サイト | 中身 |
| --- | --- |
| [大型店日報](https://ogataten-nippo.com/) | 大規模小売店舗立地法の届出 |
| このサイト | 競売・公売・国有財産・公有財産 |
| 開発届出サイト（未着手） | 開発許可の届出 |

3つが同じ形の `index.json` を出す。`city_code`（総務省の5桁）と
`addr_key` がそろっているので、あとから「この土地について3つのサイトが
何を言っているか」を1枚にまとめられる。

### 住所のそろえ方（`common/addr.py`）

書き方が違っても、同じ土地なら同じ鍵になる。鍵は**粗さの違う2本**を出す。

```
梅田一丁目1番1号          ┐   addr_key      → 27127|梅田1-1-1  （番地まで）
梅田１丁目１番１号        │
梅田 1丁目 1番 1号        ├→
梅田1-1-1                 │   addr_key_town → 27127|梅田       （町丁目まで）
大字梅田1丁目1番1号       ┘
```

鍵が2本あるのは、**サイトによって出せる精度が違う**から。
こちらは競売・公売を市区町村までしか持たない。大型店日報は番地まで出せる。
片方が粗いときは `addr_key_town` で突き合わせる。跡地ファイルは粗いほうだけ出す。

やっていること: 全角→半角、漢数字→算用数字、丁目・番地・番・号→ハイフン、
「大字」「字」と空白を落とす、建物名と部屋番号は `addr` に残して `addr_key` から落とす。

手を入れたところ:

- **地名の漢数字は直さない。** 「三田市」を「3田市」にすると別の場所になる。
  直すのは「丁目・番地・番・号」の直前にある漢数字だけ
- **町名の中の数字を壊さない。** 「甲子園七番町」はハイフンにしない
  （`(\d+)番` の後ろが「町」「丁」なら町名の一部とみなす）
- **カタカナの長音「ー」はハイフンに直さない。** 建物名が壊れる
- コードが引けないときは `addr_key` を**空にする**。推測で埋めない

`common/` の中身は3つのリポジトリに**同じものをコピーして置く**。直したら3か所そろえる。

### 個別に載せる基準（`make_index.py`）

`index.json` に1件ずつ載せるのは、次のどちらかを満たすものだけ。

- **(a)** 所有者・落札者が**法人名義**（株式会社・有限会社・合同会社・一般社団法人など）
- **(b)** 物件の用途が**店舗・事務所・工場・倉庫・商業地・工業地**のいずれか

これに当たらないもの（個人名義の居宅・区分マンションなど）は1件ずつ載せず、
市区町村ごとの件数だけを `counts_by_city` に入れる。

```json
"counts_by_city": [{"city_code": "27127", "city": "大阪市北区", "count": 12}]
```

**`party` には法人名しか入れない。** 個人名義のものは空文字にする。
債務者・滞納者の名前は、そもそも行データに保存していない。

**競売と公売は、中身にかかわらず個票を出さない。**
所有者名が公表されていないので (a) を確かめる方法がなく、
`index.json` の `records` は**いつも空**になる。
実際に出るのは `counts_by_city`（市区町村ごとの件数）だけ。
個票に近いものを出すのは、次の跡地ファイルだけ。

この決まりは `tests/test_index.py` で固定してある。`about.md`（サイトの
「このサイトについて」）にも同じことを書いてある。

### 名前の欄があるかを、先に確かめる

`party_kind` の `undisclosed`（＝一次情報が名前を載せていない）は、
**地番まで出してよい**という意味になる。だからここを間違えると住所が漏れる。

| 調べたか | `party_kind` | 住所 |
| --- | --- | --- |
| 欄が無いことを**確認ずみ** | `undisclosed` | 地番まで |
| 欄はあるが読めていない | `individual` | 町丁目まで |
| **調べていない** | `individual` | 町丁目まで |

`sources.json` の `name_column` に書く。**いまは全部「未確認」。**
実物を1枚読んで確かめるまで、`undisclosed` は名乗らない。

読み取りのほうでも、名前らしき見出しが1つも見つからなかったら
`data/parse-unknown.md` に出す。**欄が無いのか、読めていないのかは
こちらには分からない。** 分からないうちはきつい側に倒す。

姉妹サイトで、近畿財務局の結果表の「契約相手方」の列を読み落としたために
名前が空になり、`undisclosed` に化けて、**個人121件の地番が出た**事故がある。
欄はあった。読んでいなかっただけだった。

### 法人を「個人」に化けさせない

裁判所も役所も、表では `㈱` を使う。丸囲みや括弧書きが抜けていると、
**法人の落札者が全部「個人」になって、升が入れ替わる。**
大型店日報の実データ（設置者1,003種）では、これを入れないと
**275種（27%）が「個人」に化けた**。入れたら22人になった。

`common/privacy.py` の `CORP_WORDS` に入れてあるもの:

- 丸囲み `㈱ ㈲ ㈳ ㈶ ㈴ ㈻ ㈷`
- 括弧書き `(株) (有) (同) (資) (名) (福) (医) (相)`（**半角と全角をそろえてから見る**。
  `(有）` という実物がある）
- 潰れた表記の `株`（「株赤ちゃん本舗」。人名に「株」は出てこない。
  **`有` は単独で入れない**。有田・有村など姓に出る）
- 外国法人 `Co. Ltd Inc LLC Corp K.K. GmbH …`
- カタカナだけ・ローマ字入り（戸籍の氏名はこの形にならない）
- 国と地方公共団体（`大阪市` `大阪市交通局` `○○町教育委員会`）

`is_corp()` が False でも氏名とはかぎらない。次の3つは別に扱う。

| 実物 | 正体 | どうする |
| --- | --- | --- |
| `未定` `物品販売業を営む店舗` `―` | 名前ではない文言 | **そのまま出す。**「個人」に変えない |
| `大阪市北区角田町３番25号` | **列がずれて住所が入った** | 個人扱い（きつい側）＋報告 |
| `三井住友ファイナンス` | 法人名が**途中で切れた** | 個人扱い（きつい側）。**置き換えも削除もしない** |

3つめは見分けがつく。**同じデータの中の別の名前の先頭部分になっていたら**、
それは切れた法人名。人名はほかの名前の頭にならない。
消すと `＆リース株式会社` だけが残る。

毎回 `data/party-audit.md` に「当事者のユニーク数・法人・個人・内訳」を出す。
**個人が1割を超えたら、語が足りていない。**

### 跡地の横断ファイル（`make_cross.py` → `data/cross/atochi.json`）

学校跡地・庁舎跡地は、競売にも公売にも出ない。自治体や国が自分の財産として
一般競争入札で売るもので、滞納処分による公売とは別の制度。

このファイルで拾うのは「**法人が使っていた工場・倉庫・店舗などが売りに出た**」ほう。
工場跡地が売れた数年後に、そこに大型店の届出が出る——という線を、
大型店日報と町丁目の鍵でつなぐためのもの。

入れるのは、次を**すべて**満たすものだけ。

本当の関門は「**人が住んでいないか**」と「**落札が済んでいるか**」の2つ。
面積はその代理でしかないので、居住用途は名指しで落とす。

**必ず落とす**（1つでも当たれば入れない）

- 建物用途に **居宅・共同住宅・アパート・マンション・寄宿舎・長屋・住宅**を含む
- 種別が「マンション」「区分所有」
- 用途地域が**住居系**（名前に「住居」が入るものすべて）
- **落札が済んでいない**（入札中・入札予定）

**残す**（ぜんぶ満たすもの）

- 種別が「土地」または「土地建物」
- 現況または建物用途が **工場・倉庫・店舗・事務所・ホテル・病院**など
- 用途地域が**工業系または商業系**
- 土地面積が **500平米以上**

落とすほうを先に見る。「店舗兼住宅」のように事業用と住まいの語が混じっていたら、
**落とすほうを採る**。

### なぜ500平米か

大阪・兵庫の都市部（近畿圏の既成市街地等）では、**開発許可が要るのが500平米から**
（都市計画法29条1項1号・同法施行令19条1項）。
それ未満の土地は、あとで開発されても許可の記録に残らないので、
跡地として拾っても「その後どうなったか」の線が引けない。

市によっては条例で300平米まで下げられる。確認できた市町村は
`common/kaihatsu_kibo.json` の `city_overrides` に書いて、**低いほうに合わせる**。
調べた結果は偵察レポートの「開発許可が要る土地の広さ」の章に一覧で出る（`kibo.py`）。

いまのところ確認できているのは、大阪府は府内一律500平米、
兵庫県は近畿圏の整備区域にあたる市町が500平米。300平米の採用は見つかっていない。

出すのは `id / kind / date / city_code / city / addr（町丁目まで）/ addr_key_town /
use / area_sqm / url / source_url / fetched_on` の12項目。
**所有者名（`party`）は出さない。** 裁判所も税務署も所有者名を公表していないので、
法人かどうかを確かめようがない。**確かめられないものは出さない。**

なお、この条件は町丁目までの住所を要求するので、
市区町村までしか持たない競売・公売の行は自動的に外れる。

**いまは出力を止めてある。** 規約の確認が済むまでファイルを書かない
（`ATOCHI=on` を付けたときだけ書く）。コードとテストは先に作ってある。

## 行儀について

相手は裁判所と役所のサーバーなので、迷惑をかけない作りにしてある。

- **robots.txt を毎回確認**し、拒否されていれば取りに行かない
- 同時に1本だけ。**1件ごとに5秒あける**（正本 3.4）
- 1日1回だけ。**中身がめったに変わらないものは月2回**
  （規約ページは1日と15日だけ。`sources.json` の `fetch_every`）
- **混んでいる（429・503）と返ってきたら、その回は打ち切る。** リトライで突破しない
- 名乗りは姉妹サイト共通の形。誰が来ているかと、どこへ言えば止まるかが分かる

  ```
  kujiraya archive bot (keibai-toukei; https://forms.gle/...)
  ```

  **404になるURLは入れない。** 確認できない名乗りは、名乗らないより不審に見える。
  相手の管理者が調べて404だったら、それだけでブロック候補になる。
  about ページを公開したら `common/site.json` の `about_url` を埋める。
  **URLはそこ1か所にしか書いていない**ので、直せば名乗りも全部変わる。

- **取れなかったら回り込まない。** 名乗りを偽らない、別経路を試さない、リトライは翌日。
  403や無応答が続くなら、その収集先は `inbox` 運用（人が手で保存）に切り替える
- **人に頼む工程は、機械が催促する。** 人は必ず忘れる。`data/inbox-todo.md` に、
  - 人に渡すのは**その裁判所のURL1本だけ**。全件を見せない
  - まだ置かれていないものを**毎回出し続ける**
  - **まもなく消えるものを先に警告する**（「あと10日で入札が終わります」）。
    競売の一覧は入札が終わると消える。過ぎてから頼んでも、もう取れない
  - 取り込んだものは台帳（`data/inbox-ledger.json`）に書いて**二度と催促しない**

BIT はアクセスログを保守・セキュリティ・統計に使うと明記している。
名乗ったうえで、1日数リクエストに収める。

## 権利まわり（まだ結論が出ていない）

- **BITの「サイトのご利用条件」は、本来の趣旨以外の目的での使用と、
  改ざん・無断転載を禁じている。** 個票の転載は正面からぶつかるのでしない。
  一覧の数値を集計して統計にする行為が「目的外」に当たるかは**弁護士確認事項**で、
  確認が済むまで公開ページには「試作版」と書く（DESIGN 10章）
- 国税庁の公売情報サイトは**公共データ利用規約（第1.0版）＝ CC BY 4.0互換**。
  出典を書けば加工・商用できる
- 自治体は個別確認。大阪市はCC BY 4.0を明記しているが、ページごとに読み直す
- **数値や事実に著作権はない**ので、数字を取り込んで自分で表やグラフにするのはよい
- **文章表現には著作権がある**ので、本文をそのまま並べない
- 取ってきたページそのもの（`data/raw/`）は**調べるための控え**であって、
  そのまま再公開するものではない。だからこのリポジトリは非公開にしてある

### 弁護士に見せる材料（`data/terms/`）

`terms.py` が、BIT・国税庁・大阪府・兵庫県・大阪市・神戸市の規約ページから
**条文の全文**を抜いて `data/terms/<id>.txt` に残し、偵察レポートの末尾にも章を足す。
要約ではなく元の文そのものを置くのは、そのまま相談の材料にするため。
取ってきた日の控えなので、あとで文面が変わっても、そのとき何が書いてあったかが残る。

あわせて「どの条文が**集計**（数字だけ使う）に効き、どの条文が**転載**
（そのまま載せる）に効くか」の当たりを `terms.py` の `NOTES` に書いてある。
**これはこちらの読みであって、結論ではない。**

いちばん効くのは BIT の1文で、ここが「集計は目的外か」の論点そのもの。
なお BIT を運営しているのは最高裁判所から委託を受けた**私企業**（株式会社日立社会情報サービス）で、
規約はその会社が置いたもの。相手が国ではない点も、あわせて見てもらう。

## 人が手で保存するもの（`inbox/`）

BIT の物件一覧・売却結果・取下げ・過去データは、**普通のURLで開けない**。
トップから先へ移るのは JavaScript の画面遷移（POST）で、リンクになっていない。
**2026-09-15 に確認した。** 回り込む（リンクを偽装してPOSTを真似る）ことはしない。
なので、この4つだけは人がブラウザで開いて保存する。

保存のしかた:

1. BIT で見たい画面を出す（裁判所と種別を選んで検索する）
2. **表示件数を「全て」にする**
3. ブラウザの「名前を付けて保存」で **「Webページ、HTMLのみ」** を選ぶ

## 記事の種（月次のコンテンツ源）

このサイトは統計を出すだけでなく、切り口を変えて記事・コラム・SNSのネタを作る源にする。
何を、どの頻度で、どう書くかは `docs/kiji-no-tane.md` に書いてある。

- **暦**（来月どこで何回開札があるか）＝毎月変わる。月次記事の本体
- **制度**（手続にかかる日数、欄の意味、農地の扱い）＝ほぼ変わらない。常設ページ
